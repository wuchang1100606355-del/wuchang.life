# 8D ADI 狀態場模型

## 證據等級

由低至高：

1. `觀察`：路徑、大小、時間等中繼資料。
2. `引用`：明確匯入、呼叫、結構鍵或命令入口。
3. `完整性`：內容雜湊或不可變清單一致。
4. `驗證`：精確測試或驗證器可重現通過。
5. `來源`：身分簽章或可信產生收據。
6. `權威`：正式權威指標或決定收據有效。
7. `效果`：正式執行路徑與效果證據閉合。

高層級不得由低層級自動推導。例如雜湊一致不等於來源真實，測試通過不等於正式部署。

## ADI 分析座標

這是技能內的定位格式，不取代專案正式 ADI 定義：

```json
{
  "node": "節點識別",
  "root": "實際根目錄",
  "worktree": "工作樹識別",
  "revision": "版本或快照識別",
  "path": "相對路徑",
  "symbol": "函式、結構或入口，可省略",
  "authority": "正式／候選／未知／失效",
  "lifecycle": "草稿／候選／驗證／正式／停用",
  "observed_at": "含時區時間",
  "evidence_level": "觀察至效果"
}
```

```json
{
  "existence": "未知／不存在／存在／墓碑",

  "content_identity": "未知／中繼資料／已雜湊／不可變",
  "persistence": "暫時／已記錄／耐久／已複寫",
  "authority": "未知／未授權／失效／有效／衝突／撤銷",
  "dependency": "未知／斷鏈／閉合／循環／衝突",
  "effect": "未知／未接線／已接線未啟用／有效果／失敗",

```

各軸彼此獨立。檔案可以「測試通過但未授權」、「已複寫但未生效」或「已生效但證據過期」。

## 狀態場節點與關係

節點類型：

```text
檔案｜符號｜結構定義｜設定｜政策｜測試｜證據｜權威決定｜執行服務｜外部介面
```

關係類型：

```text
需要｜供給｜實作｜隸屬｜產生｜使用｜匯入｜呼叫｜讀取｜寫入｜驗證｜授權｜衍生｜取代｜路由｜部署｜證明｜衝突｜影響｜造成
```

每條關係記錄來源、目標、固定方向、條件、證據路徑、證據等級、適用環境、時間、反證與未知範圍。

`造成` 必須有機制與可重驗證據；只有時間先後時只能記錄為 `影響／推論`。

## 群組判定

- `閉合供需`：上游供給滿足需求，下游有明確引用，驗證可重現。
- `供給孤島`：存在產物或能力，但未發現可信下游；不代表可以刪除。
- `需求斷鏈`：入口存在，但必要上游、結構、版本或權威缺失。
- `重複供給`：多個節點供給相同能力，沒有明確正式選擇。
- `候選未接線`：有程式或測試，沒有正式入口與效果證據。
- `權威衝突`：不同有效來源對同一座標給出互斥決定。
- `時間錯置`：下游或證據早於其宣稱使用的上游版本。

## 影響傳播

```text
變更節點
  → 直接消費者
  → 結構與介面相容性
  → 測試與驗證器
  → 執行入口與部署單位
  → 證據與權威決定
```

傳播分成 `可能路線`、`靜態可達`、`測試重現`、`執行觀測`。遇到動態載入、反射、外部服務、資料庫觸發器、排程器、訊息路由、人工程序或未解析生成碼時停止，標示未知邊界。

## 狀態轉換

- 觀察：未知轉為存在或不存在。
- 內容改變：建立新座標，舊驗證改為過期或未測試。
- 映射：新增宣告或推論關係，不提升權威或效果。
- 驗證關係：推論或觀察轉為已驗證。
- 閉合依賴：所有必要依賴已驗證且相容，斷鏈轉閉合。
- 核准：只有明確權威證據才能轉為有效。
- 接線：未接線轉為已接線未啟用；須有效果收據才能轉為有效果。
- 持久化：依獨立收據由暫時轉為已記錄、耐久、已複寫。
- 撤銷或取代：重評所有下游與過往證據。
- 保留：必要欄位未知或證據衝突時禁止自動前進。

## 送達狀態不可壓扁

- 工作區檔案安全，不代表包含它的提交與全部祖先安全。
- 本機提交存在，不代表遠端已收到。
- 遠端收到候選分支，不代表主線已包含。
- 主線包含，不代表已部署、已啟用或有效果。
- 提交簽章、版本寫入權、審查核准與總場正式權威是四個獨立座標。
- 多遠端沒有共同原子性；逐遠端保存結果，部分成功不得改報全部成功或全部失敗。
- 子模組、大型檔案物件與上層版本各自需要送達收據。

每個送達單位至少記錄：目的、精確納入與排除路徑、提交集合、必要祖先、相依單位、閉環狀態、真實風險、驗證證據、權威範圍、送出節點、目標儲存庫識別、清理後遠端指紋、目標參照與判定。

完整規則見 [delivery-routing.md](delivery-routing.md)。

## 無 Git 的最低替代條件

若要宣稱具備與成熟版本控制相當的保存能力，至少另行證明：

- 位元組、檔案模式與符號連結可逆保存。
- 內容定址、防碰撞驗證與不可變物件。
- 完整父子與多父歷史、原子多檔快照。
- 作者身分、簽章驗證及權威分離。
- 多人併發、分支、合併、衝突保存與人工裁決。
- 遠端同步、權限、斷線續傳、備份與災難復原。
- 完整性檢查、損壞修復與實際還原演練。
- 與既有版本庫往返匯入匯出且不遺失歷史拓撲。

未閉合前，只能宣稱「狀態場分析與決策層可取代 Git 中心工作方式」，不能宣稱已取代版本儲存系統。
