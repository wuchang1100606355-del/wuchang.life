# Odoo 咖啡館安全菜單管理介面 V1

## 目前狀態

這是原始碼已完成、尚未啟用的產品級候選。尚未執行 Odoo 模組升級、資料庫寫入、重啟或公開部署，因此不能宣稱正式營運環境已具備此介面。

## 人的治理原則

人就是人。一位自然人只使用一個 Odoo 帳號；開發者、協會負責人、咖啡館負責人、社工、專利師與法務顧問等職務，是同一人的責任標籤，不拆成多個假帳號。

系統保存的是每次事件的四個必要事實：

- 誰：單一操作帳號及治理人員識別。
- 哪裡：協會、商家、Odoo 公司及店家座標。
- 何時：提出、確認與生效時間。
- 做什麼：單一商品的新增、修改、封存或重新上架，以及修改前後差異。

店長直接維護與遠端候選／確認都寫入既有 `wuchang.cafe.ai.eventbook` 事件簿；事件簿的操作人以單一帳號識別，菜單圖片只留雜湊，不存入事件 payload。

同一人兼任全部職務時，不虛構第二位審核人。遠端支援候選仍不會自動生效；同一帳號必須稍後重新檢視差異並按下明確確認，形成第二個人為事件。

## 店長操作介面

店長只進入「咖啡館菜單」，不進入完整 Odoo 商品、庫存或 POS 管理設定。商品庫以一張卡代表一個商品，表單僅露出：

- 商品名稱
- 售價
- POS 分類
- 商品圖片
- 口味、甜度、溫度共用規格
- 上架狀態

不再販售時只能封存，不能刪除。名稱或價格改變時，底層事物碼不變；封存後保留原碼與歷史證據。

## 遠端支援流程

1. 同一操作帳號選擇本次事件情境是「店長維護」或「遠端支援」。
2. 遠端支援填寫觀察到的問題、指定一個商品及建議修改。
3. 系統建立 L3 8D 候選，封存修改前雜湊、修改後雜湊、診斷理由雜湊及誰／哪裡／何時／做什麼。
4. 候選只進入待確認狀態，不直接修改商品、不建立正式訂單、不收款。
5. 綁定的同一自然人使用同一帳號重新檢視前後差異，填寫結論後明確按下「核准並套用」。
6. 套用前再次比對商品快照與候選雜湊；任何漂移都會阻擋。
7. 成功後建立核准封印，留下確認事件的誰／哪裡／何時／做什麼。

## 防呆與最小權限

- 菜單負責人群組不繼承 Odoo `point_of_sale.group_pos_manager`。
- 遠端支援單獨存在時只能讀商品及提出候選，不能直接寫商品。
- 同一帳號同時具備兩種責任時，正常店長維護不會被遠端支援標籤誤擋；事件情境決定流程。
- 菜單表單採欄位白名單，拒絕成本、供應商、庫存、會計及其他 ERP 欄位。
- 價格必須是非負數字，名稱不可空白。
- 每個營運公司只接受一筆有效的團體會員負責人綁定。
- 審核單不可刪除；送出後除人審結論外不可修改。
- 遠端修正必須填寫診斷理由與人審結論。

## 主流 POS 介面取向

本介面採用主流 POS 的共同操作習慣，但不複製其品牌視覺：

- Square：由 Item Library 集中新增、編輯商品、分類與 modifiers。<https://squareup.com/help/us/en/article/8335-create-and-edit-items>
- Shopify：商品頁先處理名稱、價格，再逐步補充選項與其他資料。<https://help.shopify.com/en/manual/products/add-update-products>
- Shopify：variants/options 以結構化選項附著於商品。<https://help.shopify.com/en/manual/products/variants/add-variants>
- Toast：菜單、群組、子群組與 modifier groups 分層管理。<https://central.toasttab.com/articles/Knowledge/Menus-Menu-Groups-and-Subgroups>
- Lightspeed：商品與分類由集中式商品管理流程維護。<https://retail-support.lightspeedhq.com/hc/en-us/articles/360036080494-Adding-items-and-inventory>

落地取捨是「高頻欄位先出現、技術證據另分頁、共用規格集中管理、刪除改為封存、遠端支援改為候選」。

## 啟用邊界

啟用此候選會新增 Odoo 欄位、模型、ACL 與檢視，必須經明確授權後執行模組升級及資料庫寫入。本輪依工作區規範保持：不升級模組、不寫資料庫、不重啟、不公開發布。
